# AGENTS.md

A small notes app (Vite + React + TypeScript) built to be safe for coding agents to change. Rules here are enforced by CI, not by good intentions: if a rule matters it has a gate, and if a gate fails the change is not done. The gates catch the shapes a careless contributor writes; they are not a boundary against deliberate evasion (see "What the gates are").

## Before any PR
Run `npm run gate` and attach the verify report (`artifacts/<timestamp>/*/report.md`) to the PR. `gate` runs, in order: `lint`, `typecheck`, `check:deps`, `check:features`, `test:guardrails`, `verify:coverage`, `verify:all`, `verify:selftest`. Do not skip a step, do not edit a gate to make it pass. If a gate seems wrong, say so in the PR and change the gate in its own commit.

## Why the layout looks like this
Contributors, human or agent, arrive with a narrow prompt, a few nearby files and no full model of the app. They copy the nearest working pattern, edit the file that is already open, take the shortest path that compiles and avoid deleting code whose callers they cannot see. This repo treats that as a design input (the agent-friendly architecture contract, see `../templates/guardrails/architecture-contract.md`): the locally obvious change should be the globally correct one, forbidden dependencies fail mechanically, every durable value has one writer, new work adds isolated files instead of branches in shared roots, and every unsafe shortcut fails with an error that names the supported path.

## Architecture map
```
src/
  main.tsx                 entry: starts main, hydrates the notes through `@/client`, mounts the shell with the app name
  app-config.ts            app-owned constants (the app name); the framework receives them as props and never names the app
  framework/               tiny standalone package: feature discovery + shell. Imports nothing from src.
  client/                  the one writer of durable notes state
    commands.ts            builds the store and keeps it private (`local/store-stays-private` rejects the common ways of exporting it); its commands write each state change out in their own body, and `local/writer-takes-data` rejects exports that take a function. Exports intent commands (`hydrateNotes`, `createNote`, `selectNote`, `updateNote`) + `useNotesState`; no command accepts a whole list of notes or a whole state, because there is no setter to call. Defines `NotesState`
    index.ts               public surface: commands + useNotesState
  features/<feature-id>/   one folder per feature, self-contained
    feature.tsx            reserved file: default-exports defineFeature({ id, title, order, slots })
    index.ts(x)            the only file other features may import
  electron/main/           stand-in for the Electron main process
  electron/renderer/       stand-in for the Electron renderer process
  shared/                  the `Note` and `DeepReadonly` types (`NotesState` lives in `client/commands.ts`), the store factory (deep-freezes every state it holds; importable only by its two listed owners), the IPC contract; imports nothing above it
.agents/skills/verify-app/ how to run and verify the app; references/features/ is the feature map
scripts/                   check-features, verify-coverage, verify CLI + scenarios, guardrail tests
guardrail-fixtures/        one deliberately violating example per rule (never imported by the app)
```
Features: `sidebar`, `editor`, `search`. Feature docs, selectors and entry-point ids: `.agents/skills/verify-app/references/features/`.

Imports: use `@/` for anything outside your own directory and `./` inside it. Another feature is reachable only as `@/features/<id>` (its index). App state is reached only as `@/client`.

## Add a feature (shortest path)
There is no code registry to edit; the only shared edit is one index line in the feature map. A feature is discovered from `src/features/<id>/feature.tsx`.
1. Create `src/features/<id>/` with `index.ts` (public export), your component(s), and `feature.tsx`:
   `export default defineFeature({ id: '<id>', title: '...', order: 40, slots: { main: MyComponent } })`. Slots: `topbar`, `left`, `main`, `overlay`. Read and change notes through `@/client`.
2. Write `.agents/skills/verify-app/references/features/<id>.md` (Sub-features list with ids, How to get to it, Driving it) and add one index line to that directory's `README.md`: ``- [`<id>`](<id>.md) — scope``.
3. Add `scripts/verify/scenarios/<id>.ts` exporting `scenarios` with `covers: ['<sub-feature-id>', ...]`, and tag the assertion that proves each id: `expect(name, expected, read, { reaches: '<sub-feature-id>' })`. Watch each scenario fail once before trusting it.
4. `npm run gate`.

The guardrail test `adding a feature is only new files` does exactly this in a sandbox with a `ping` feature: it runs lint, typecheck, check:deps, check:features and verify:coverage, then a real `verify --feature ping`, and checks that the feature reached the bundle without editing any code file.

## What the gates are
Static rules (lint, depcruise, typecheck) catch the common shapes a careless agent writes. TypeScript analysis is not sound (structural `readonly`, `Map` and array containers, `Reflect`, re-exports through allowed files, copied files), so they are not a boundary against deliberate evasion. The rest is covered by three other things: runtime freezing (a write to state throws), verification scenarios that run the real app, and human review. Each claim below is stated only as far as a fixture or test proves it; where a claim has known holes they are listed under "Not enforced". Prefer making the wrong thing structurally absent (there is no setter to call, state is frozen) to adding a rule that detects one spelling of it.

## Not enforced: review items
No check backs these. A reviewer owns them, and each stays here until a check exists. Adding a rule for each escape below is deliberately not the plan: see "What the gates are".
- **A `reaches` tag on an assertion that cannot fail**, for example `expect('x', true, async () => true, { reaches: 'id' })`. `verify:all` counts the tag, not what the assertion reads. Check that the tagged assertion reads the UI and would turn red if the entry point broke; "watch each scenario fail once" (Add a feature, step 3) is the practice, not a gate.
- **A parallel store of notes state in a feature.** `search-store.ts` is the sanctioned private UI store. `create-store-is-private` limits who may build a store but not what it holds, so a store of notes data in an allowed file is a review item.
- **Readonly is compile-time, and structural.** `function tidy(note: { title: string })` accepts a `Note`, and `as` casts and `any` hide one too; `typecheck` does not see that. At runtime the freeze throws for plain objects and arrays; a `Map`, `Set`, `Date` or class instance placed in state is not made immutable.
- **Escapes from `create-store-is-private`.** The importer list is a path list, so a re-export of `createStore` through an allowed file (`search-store.ts`) and a copy of `create-store.ts` at another path are not seen.
- **Escapes from `local/store-stays-private`.** A typed alias of the factory (`const make: Builder = createStore`) hides the call from the rule.
- **Escapes from `local/writer-takes-data`.** An exported `Map`, array, `EventTarget` or object property that holds updaters; an `object` or `{}` parameter plus a cast; a callable nested deeper than 6 levels; an overload whose signature hides the function in the implementation; a setter hung on `window`; `as unknown as`. A command that accepts a whole list or state (the removed `resetNotes(notes)` was one: used as Delete it produced duplicate ids) is also not detected. There is no setter to call now, and a reviewer keeps it that way.
- **`skip:` reasons.** Any non-empty reason is accepted. `verify:coverage` cannot tell a real blocker from a convenience; a reviewer reads the reason.
- **Controls without docs.** `check:features` goes from the doc to the markup only. A new button, label or `role` that no feature doc names is not detected.
- **Selector literals anywhere under the feature folder.** Any `attr="value"` string literal under `src/features/<id>/` satisfies a doc selector, wherever it is. Doc selectors written without quotes (`[role=listbox]`) are not compared.
- **Deleting a doc line.** Removing an entry point's line, together with its `reaches` tag, shrinks the coverage set and nothing goes red.
- **Selector docs are compared as strings.** A string found in a component nothing renders passes, `aria-current` and `aria-selected` are not compared, and a value set through a variable (`aria-label={label}`) is read as missing.
- **Updater code that `commands.ts` imports.** `store.set(importedFunction)` is allowed: the function is code in this repo, not something a caller handed in, and it runs only when a command calls it.

## Verification and selectors
`npm run verify -- --feature <id>` runs the real app in headless Chromium and writes screenshot, console log, CDP trace and a report. `npm run verify -- --help` prints the usage, `npm run verify -- doctor` checks the instance first. An explicit `--port` that something else holds is refused (exit 3), and verify only drives a server whose `/.verify-build.json` carries the nonce of the build it just made. See `.agents/skills/verify-app/SKILL.md`. "It type-checks" is not verification; attach the report.

Selectors: prefer ARIA labels and `data-component` / `data-action-id`; there are no test ids in this app. The feature docs list the selectors for each feature; keep them in sync when you change markup. `check:features` fails (`feature-selector-drift`) when an `aria-label`, `data-component`, `data-action-id` or `role` value named as `[attr="value"]` or `[attr='value']` in a feature file is not assigned as a string literal anywhere in `src/features/<id>/`. It does not compare ARIA state (`aria-current`, `aria-selected`), text or behaviour, does not know whether the file is rendered, and cannot see values set through variables (see "Not enforced").

## Fixing a gate failure
Fix the code, not the gate. A review comment that a human makes twice should become, in this order of preference: an API or runtime behavior that makes the wrong thing absent (no setter to call, state frozen), a lint rule, a dependency rule or a test with a fixture in `guardrail-fixtures/` and a case in `scripts/guardrails.test.ts`, seen failing first. Claim only what a fixture proves, and list the shapes it does not cover under "Not enforced". A rule keyed on module paths and types survives a rename, alias or namespace import (the store rules started as a name match and were bypassed by `import { createStore as make }`), but it is still a detector of spellings; when a review finds a new way around one, ask what structural change removes the whole class before adding another rule.
